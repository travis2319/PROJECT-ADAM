\section{System Architecture and Methodology}

The proposed Automotive Diagnostic and Activity Monitoring (ADAM) system is a modular and scalable solution that integrates hardware sensors, software analytics, and cloud-based infrastructure to collect, process, and visualize real-time vehicular data. The architecture is designed to support both diagnostic analysis and driver behavior profiling, offering both forensic insight and real-time feedback through a mobile dashboard.

\subsection{System Overview}

The ADAM system consists of four key components:

\begin{itemize}
    \item \textbf{Hardware Layer:} In-vehicle data acquisition using OBD-II and external sensors.
    \item \textbf{Edge Device and Local Storage:} Data logging using Raspberry Pi and SD card.
    \item \textbf{Cloud-Based Machine Learning Pipeline:} Preprocessing, inference, and analytics.
    \item \textbf{Mobile Application:} User-facing interface for visualization and alerts.
\end{itemize}

\subsection{Hardware Integration}

The system is built around a Raspberry Pi 5, which interfaces with a standard OBD-II adapter supporting CAN (ISO 15765-4) and K-Line (ISO 9141-2) protocols. In addition to retrieving internal engine diagnostics, the system integrates external sensors such as:

\begin{itemize}
    \item \textbf{Neo-6M GPS module} – For geolocation and speed tracking.
    \item \textbf{MPU-6050 IMU} – To measure acceleration and orientation.
    \item \textbf{SW-420 vibration sensor} – To detect abnormal vibrations indicative of mechanical faults.
\end{itemize}

All raw sensor data is logged to a local microSD card, enabling forensic data retention in case of network unavailability or vehicle incidents.

\subsection{Machine Learning-Based Data Processing}

To enhance vehicle monitoring capabilities, four supervised machine learning models were developed, focusing on:

\begin{enumerate}
    \item \textbf{Driver Behavior Analysis}
    \item \textbf{Fuel Consumption Estimation}
    \item \textbf{Predictive Maintenance}
    \item \textbf{Engine Health Performance}
\end{enumerate}

These models are trained on structured vehicular datasets and are periodically updated through retraining pipelines.

\subsection{Cross-Platform Mobile Application}

A mobile application, developed using the Expo framework, acts as the primary interface for end-users. It presents real-time diagnostic summaries, trends over time, and user-specific notifications using dynamic visualizations. The app is compatible with both Android and iOS, offering accessibility to a wide user base.

\subsection{Model Training and Feature Importance Analysis}

To classify engine health based on sensor features, a Random Forest classifier was trained using a domain-labeled dataset named \texttt{Sensor-count\_Breeza-Verna-Version4.xlsx}. After preprocessing, including trimming column headers and dropping incomplete entries, the dataset was split into features and labels.

An 80:20 train-validation split was applied, followed by training a 100-tree Random Forest model. Performance was evaluated using standard metrics such as precision, recall, and F1-score. Feature importance scores were then extracted and visualized, enabling interpretation of the most impactful sensor inputs. The trained model was serialized as \texttt{engine\_model.joblib} for deployment on the Raspberry Pi.

\section{OBD-II and Diagnostic Parameters}

On-Board Diagnostics II (OBD-II) is a standardized system implemented in all vehicles manufactured after 1996, primarily aimed at monitoring vehicle emissions, engine performance, and subsystem faults. Developed by the Society of Automotive Engineers (SAE), the OBD-II specification includes a 16-pin connector that grants access to the vehicle’s Electronic Control Unit (ECU).

\subsection{OBD-II Functionality in ADAM}

In the ADAM system, the OBD-II interface serves as a primary data acquisition point, capturing key engine parameters and fault indicators in real time. The Raspberry Pi communicates with the OBD-II adapter via USB or UART, retrieving information encoded in hexadecimal format.

Two major types of codes are used for ECU communication:

\begin{itemize}
    \item \textbf{Parameter IDs (PIDs):} Used to request real-time sensor data (e.g., speed, RPM, fuel level).
    \item \textbf{Diagnostic Trouble Codes (DTCs):} Used to indicate errors or faults in vehicle subsystems.
\end{itemize}

\subsection{Parameter ID (PID) Communication}

When a PID request is sent to the ECU (e.g., `010C` for RPM), the ECU responds with a data frame in hexadecimal. This frame includes the requested values, which are decoded using standard formulas. For example:

\begin{itemize}
    \item PID `0C` (Engine RPM): Response = `41 0C 1A F8` → RPM = ((1A × 256) + F8) / 4
    \item PID `0D` (Vehicle Speed): Response = `41 0D 3C` → Speed = 60 km/h
\end{itemize}

\subsection{Diagnostic Trouble Codes (DTCs)}

DTCs provide encoded fault messages that indicate malfunctions in systems such as ignition, emissions, or engine timing. A typical DTC (e.g., `P0302`) can be decoded as:
\begin{itemize}
    \item \texttt{P} – Powertrain
    \item \texttt{03} – Misfire
    \item \texttt{02} – Cylinder 2
\end{itemize}

In ADAM, DTCs are parsed, logged, and flagged in the mobile app to prompt maintenance actions.
