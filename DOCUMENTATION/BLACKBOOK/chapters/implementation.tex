\section{INTRODUCTION}

This chapter discusses the implementation of our system, which consists of three primary components: the hardware setup, cloud-based storage and analysis, and a mobile application for user interaction.
\subsection{Hardware Implementation}

The hardware implementation consists of multiple sensors connected to a Raspberry Pi 5, serving as the central edge computing unit for real-time data acquisition, local processing, and cloud transmission. The system integrates several key components:

\begin{itemize}
    \item \textbf{Raspberry Pi 5:} Acts as the central processing unit, efficiently handling real-time data acquisition, local computation, and sensor coordination.
    \item \textbf{GPS Module (NEO-6M):} Enables accurate vehicle location tracking and route history monitoring.
    \item \textbf{Vibration Sensor (SW-420):} Detects collision events and unusual vibrations indicative of accidents or aggressive driving patterns.
    \item \textbf{Gyroscope Module:} Monitors vehicle orientation, tilt, and angular motion for advanced motion analysis, including rollover detection and abrupt turn identification.
    \item \textbf{Power Management:} Connected to the vehicle battery via a relay system to prevent direct current cut-off when the car is turned off, ensuring continuous monitoring capability.
\end{itemize}

\subsubsection{CAN Message Structure}

The Controller Area Network (CAN) protocol is used to retrieve and interpret data from the vehicle’s electronic control units (ECUs). A typical CAN message frame consists of key fields such as identifier, data length code (DLC), and data payload, which collectively define how information is transmitted between modules in real time.

\begin{itemize}
    \item \textbf{Identifier:} Uniquely identifies the type of message or the sender ECU.
    \item \textbf{DLC (Data Length Code):} Specifies the number of bytes in the data field (0–8).
    \item \textbf{Data Field:} Contains the actual payload, such as sensor values or control commands.
\end{itemize}

func FetchHandler(c *fiber.Ctx) error {
    pool := database.GetPool()
    conn, err := pool.Acquire(context.Background())
    if err != nil {
        log.Printf("DB connection error: %v", err)
        return c.Status(500).JSON(
            fiber.Map{"error": "DB error"})
    }
    defer conn.Release()

    table := "dataset"
    query := `SELECT * FROM ` + table
    rows, err := conn.Query(context.Background(), query)
    if err != nil {
        log.Printf("Query error: %v", err)
        return c.Status(500).JSON(
            fiber.Map{"error": "Query error"})
    }
    defer rows.Close()

    fields := rows.FieldDescriptions()
    columns := make([]string, len(fields))
    for i, f := range fields {
        columns[i] = string(f.Name)
    }

    var result []map[string]interface{}
    for rows.Next() {
        row := make([]interface{}, len(columns))
        ptrs := make([]interface{}, len(columns))
        for i := range row {
            ptrs[i] = &row[i]
        }
        if err := rows.Scan(ptrs...); err != nil {
            log.Printf("Scan error: %v", err)
            return c.Status(500).JSON(
                fiber.Map{"error": "Scan error"})
        }
        rowMap := make(map[string]interface{})
        for i, col := range columns {
            if v, ok := row[i].([]uint8); ok {
                rowMap[col] = string(v)
            } else {
                rowMap[col] = row[i]
            }
        }
        result = append(result, rowMap)
    }

    if err := rows.Err(); err != nil {
        log.Printf("Row iteration error: %v", err)
        return c.Status(500).JSON(
            fiber.Map{"error": "Read error"})
    }

    return c.JSON(fiber.Map{
        "data":    result,
        "count":   len(result),
        "columns": columns,
    })
}

\section{FASTAPI}
    Once stored, the diagnostic data is accessed by a FastAPI-based application layer. This server plays a central role in processing data, serving APIs to external interfaces, and executing real-time and scheduled analysis tasks. One of its most critical roles is the application of Machine Learning (ML) models trained on historical vehicle data to derive predictive insights.
    \begin{enumerate}
        \item \textbf{Emissions Diagnostic:} 
            The emissions router (\path{routers/emissions.py}) processes real-time sensor data to determine emission compliance status using the EnhancedCarEmissionsMLModel. When a request is received, the router accepts CSV uploads or JSON payloads containing sensor readings such as CO levels, NOx concentrations, and particulate matter measurements. The data is validated using Pydantic models before being passed to the emissions model, which preprocesses the sensor values, applies Indian emission standard thresholds, and generates compliance classifications using a trained Random Forest classifier. The router returns structured JSON responses containing compliance status, confidence scores, and detailed sensor analysis, along with optional confusion matrix visualizations for model performance assessment.
        \item \textbf{Engine Health Diagnostic:} 
            The ADAM system includes an advanced engine health monitoring module that leverages a \textbf{Random Forest Classifier} trained on OBD-II vehicle telemetry data. This model classifies engine conditions as either \textit{"Good"} or \textit{"Needs Attention"}, enabling predictive maintenance recommendations and contributing to enhanced vehicle safety and operational efficiency.

\subsubsection*{Workflow}

\begin{itemize}
    \item OBD-II diagnostic data including parameters like RPM, throttle position, coolant temperature, voltage, fuel trim values, and misfire counts are preprocessed and labeled as healthy or faulty.
    \item The dataset underwent cleaning by dropping non-numeric and irrelevant columns, encoding categorical labels, coercing all data to numeric types, and handling missing values via median imputation.
    \item Features were standardized using \texttt{StandardScaler}, and the data was split into \textbf{80\% training} and \textbf{20\% testing}.
    \item A \textbf{Random Forest Classifier} with 150 estimators was trained and evaluated.
    \item Cross-validation using \textbf{5-fold StratifiedKFold} was performed to ensure reliable model performance.
\end{itemize}

        \subsection{Rule-Based Diagnostic Framework}

Unlike machine learning modules, the predictive maintenance router adopts a deterministic, threshold-based diagnostic approach derived from OEM specifications and operational data. This ensures interpretable, consistent outcomes across vehicle types.

As shown in \textbf{Figure~\ref{fig:predictive-maintenance-flowchart}}, real-time OBD-II sensor data is evaluated against predefined thresholds for key subsystems:

\begin{itemize}
    \item \textbf{Engine Lubrication:} Run-time over 7,500 units triggers oil change scheduling.
    \item \textbf{Air Intake:} Manifold pressure outside 95–105 kPa signals filter replacement.
    \item \textbf{Ignition:} Non-zero misfire count prompts spark plug inspection.
    \item \textbf{Electrical:} Control voltage below 11.5V flags battery compromise.
    \item \textbf{Throttle:} Sensor deviation exceeding 10\% indicates recalibration.
    \item \textbf{Fuel Mixture:} Oxygen sensor voltage outside 0.8–1.2V suggests irregularities.
    \item \textbf{Cooling:} Coolant temperatures above 110°C indicate inefficiency.
    \item \textbf{Emissions:} Active DTCs flag emission system maintenance needs.
\end{itemize}

\subsection{Maintenance Classification and Reporting}

Maintenance outcomes are categorized into:

\begin{description}
    \item[\textbf{Critical:}] Immediate intervention required.
    \item[\textbf{Warning:}] Scheduled maintenance advised.
    \item[\textbf{Good:}] No issues detected.
\end{description}

Post-diagnosis, the system generates reports detailing component-specific findings, recommended actions, and maintenance priorities. This rule-based strategy ensures transparent, actionable diagnostics without reliance on opaque models.
